GenAI Gateway With APIM

Give AI applications a governed model endpoint. Control consumption, route around unavailable backends, and decide when cached answers are safe to reuse.

L300Optional reference~20 min additional

What Is an AI Gateway?

The AI gateway extends API Management's existing API gateway; it is not a separate offering.

Source: Microsoft Learn, AI gateway capabilities

You publish model APIs behind APIM so applications use a controlled entry point instead of distributing provider credentials to every team. You apply authentication, token budgets, routing, and observability at that boundary. Your models still run in their own hosting services.

Govern Access

Authorize consumers and authenticate the gateway to model backends. Use products and subscriptions to package access for different applications or use cases.

Manage Shared Capacity

Control token consumption per consumer and choose how requests reach provisioned or pay-as-you-go deployments.

Evaluate AI-Specific Controls

Add token metrics, semantic caching, and content safety where the model schema and gateway support them.

How It Works

Separate the consumer contract from backend selection. The gateway can front Azure OpenAI deployments and other reachable model REST endpoints; network reachability alone does not make every AI policy compatible with a custom model.

  1. Onboard the contract: import a model API and check its schema, operations, and authentication. Current Azure OpenAI guidance supports import from Microsoft Foundry or an OpenAPI specification.
  2. Identify and authorize the consumer: validate its identity and permissions before forwarding requests or looking up shared answers.
  3. Apply the selected controls: enforce consumer budgets, optionally check a semantic cache, and select an approved backend. Authenticate backend calls separately.
  4. Observe the outcome: record latency, failures, and available token usage, including denied requests and cache behavior.

Govern Tokens, Not Just Requests

Combine request throttling with token controls when you need both burst protection and a consumption budget. Derive a consumer's counter key from a validated identity or an enforced APIM subscription, not a caller-supplied tenant header that anyone can change.

This illustrative inbound fragment requires an API with Subscription required enabled and a valid subscription context. The numbers are example consumer budgets, not Azure service limits. Use distinct counter keys when separate APIs or scopes need independent budgets.

Illustrative inbound policy fragment 
<llm-token-limit
    counter-key="@(context.Subscription.Id)"
    tokens-per-minute="1000"
    token-quota="100000"
    token-quota-period="Monthly"
    estimate-prompt-tokens="true" />

Understand Rejection

llm-token-limit returns 429 when the token rate is exceeded and 403 when the configured period token quota is exceeded. Your client must distinguish these from backend failures.

Account for Estimation

Prompt estimation can reject work before a backend call, at a performance cost. Without it, enforcement uses returned usage after the call. Streaming estimates both prompt and completion tokens regardless of that setting.

Know the Boundary

Concurrent calls can temporarily exceed a budget. Token counts are tracked independently at each gateway, including regional and workspace gateways; they are not an instance-wide accounting ledger.

Important: consumer budgets do not increase a model deployment's capacity or provider quota. Test actual usage, estimated usage, concurrency, and streaming separately.

Route for Capacity and Recovery

Use backend entities to centralize endpoint configuration and select a pool rather than scattering endpoint URLs through policies. Round-robin spreads calls evenly; weights adjust relative distribution within a group; priority groups prefer one set of backends before another.

For a PTU-first design, place provisioned deployments in the preferred priority group and eligible pay-as-you-go deployments in a lower-priority group. Configure circuit breakers for the relevant failure conditions, including backend throttling, and accept the backend's Retry-After duration when appropriate.

Important: lower-priority pool members are used only when all backends in higher-priority groups are unavailable because their circuit breakers have tripped. Priority alone is not a token-capacity sensor, and a breaker does not itself replay the failed request.
  • Keep retries bounded: define retryable failures and a total latency budget. An ambiguous failure can mean the model already performed work; do not assume another attempt is free.
  • Check compatibility: fallback deployments must support the required API, model behavior, deployment mapping, and authorization. Stateful conversations may need affinity or an explicit migration strategy.
  • Protect residency: approve fallback regions and providers before enabling them. A gateway in one region does not guarantee where models, caches, safety services, and logs process data.
  • Design for exhaustion: return an explicit failure when no eligible backend has capacity. Spillover improves options; it cannot guarantee every request completes.

Backend load distribution and circuit-breaker decisions are approximate across distributed gateway instances. Validate behavior under load rather than treating a pool as a globally synchronized scheduler.

Evaluate Semantic Caching

Semantic caching can reuse a completion for a prompt with similar meaning, rather than requiring identical text. It needs an embeddings endpoint and a compatible external cache; it is not the gateway's ordinary built-in HTTP response cache. Current setup guidance uses Azure Managed Redis with RediSearch.

    E --> Q{Suitable cache hit?}
    Q -->|Yes| C[Return cached answer]
    Q -->|No| M[Call approved model]
    M --> S[Store eligible answer]
    S --> R[Return answer]
    class A azure
    class E,M accent
    class Q neutral
    class S data
    class C,R success

Scroll horizontally to inspect the diagram. Blue is the authorized entry, purple model work, gray the cache decision, teal storage, and green returned results. A cache hit can avoid generation but still requires embedding and lookup work.

  • Pair lookup and store: use llm-semantic-cache-lookup inbound and the corresponding store policy outbound. Size and authorize the embeddings backend independently.
  • Partition deliberately: use vary-by to separate trusted tenant or user authorization contexts. Include model, system-prompt version, or knowledge version when changing them would invalidate an answer.
  • Evaluate correctness: tune the score threshold with real prompt pairs, define a suitable lifetime, and bypass caching for personalized or sensitive answers that cannot be safely reused.
  • Protect cache misses: retain authentication and abuse controls before lookup, and follow the documented recommendation to rate-limit after lookup so a cache outage does not overwhelm the model.
Avoid: sharing answers across authorization boundaries, treating similarity as proof of correctness, or assuming embedding and cache storage cannot contain sensitive information.

Protect Prompts and Trust Boundaries

Separate Two Identities

Validate consumer tokens and required permissions at the gateway. Use the gateway's managed identity for supported model backends, with the appropriate resource-scoped role. Current Azure OpenAI guidance uses Cognitive Services OpenAI User.

Handle PII Explicitly

Managed identity authenticates a caller; it does not detect or redact personally identifiable information. The playbook describes an external processing component, such as a Function calling Azure Language PII detection, for that responsibility.

Evaluate Content Safety

llm-content-safety calls Azure AI Content Safety to check configured harmful-content categories and prompt attacks. Treat content safety, PII redaction, and authorization as separate controls.

Document which components may see prompts and completions, including embeddings, caches, safety checks, and telemetry. If a required safety or redaction dependency is unavailable, define an explicit rejection path instead of silently forwarding unprocessed content.

Restrict policy-editing permissions as well as backend credentials: policy authors can reference configured embeddings or safety backends and invoke them with their configured authentication.

Learn more: Consumer authorization and backend managed identity, content safety and backend-access considerations, PII detection and redaction, and the PII reference design.

Observe Usage Without Leaking Content

Use llm-emit-token-metric with the required Application Insights integration to emit available token usage. Choose bounded dimensions such as an approved application or cost-center classification; avoid prompt text and unbounded user-generated values.

Azure Monitor language-model logs can record model information and token usage, with optional prompt and completion capture. Start with the minimum data needed; explicitly approve message capture, retention, and log access before enabling it.
