API Design and Import

Make the public contract intentional, then import it without confusing an API definition with a working backend connection.

OpenAPI.NET 10~15 min core + reference
Reading path: contract terms, starting points, and import boundaries form the core. SOAP, WebSockets, design-first implementation, and IDE tooling extend the reference coverage.

Know Which API You Are Changing

TermMeaning for your design
Backend APIThe service that implements your operations.
Frontend APIThe contract APIM exposes to consumers. It can differ from the backend through policies.
OperationAn HTTP method and URL template that resolve to a frontend API action.
DefinitionA description such as OpenAPI; importing it does not deploy or secure your backend.

Key takeaway

In either approach, review operation names, schemas, status codes, and compatibility as consumer-facing design decisions. Generated does not mean reviewed.

Respect Import Boundaries

.NET 10 compatibility

.NET 10 generates OpenAPI 3.1 by default. APIM permits 3.1 import but does not fully process its specific constructs. These labs explicitly generate 3.0 instead of relabeling a 3.1 document.

Security is separate

OpenAPI security definitions are ignored on import. Configure subscriptions and authentication policies explicitly, and test a denied request.

Backend reachability

A locally saved definition can be imported, but the managed gateway cannot reach your laptop's localhost. Use the deployed backend hostname.

Function import

Resource import supports HTTP-triggered functions with Anonymous or Function authorization. APIM's subscription key and the Function host key protect different connections.

Modernize a SOAP Facade Deliberately

A WSDL describes SOAP operations and message shapes. APIM can import it as a SOAP pass-through API, where consumers still send SOAP, or expose a REST-style facade with policies that translate requests and responses to the SOAP backend.

ChoiceConsumer experienceDesign responsibility
SOAP pass-throughSOAP messages and operations remain visible.Review supported WSDL constructs and preserve the intended SOAP behavior.
SOAP-to-RESTHTTP resource operations are mapped to SOAP messages.Review generated URL/method choices, payload mappings, faults, and transformation policies.

For example, a consumer-facing product lookup can become a REST-style operation while the backend retains its SOAP contract. That is interface modernization, not a rewrite of the backend implementation. Test success, validation errors, SOAP faults, and namespace-dependent payloads rather than assuming an import is production-ready.

WSDL import has restrictions, including unsupported external import/include dependencies. Resolve the definition into a supported form and inspect the import restrictions before choosing this migration path. The deck's "one-click" description should not replace contract and behavior review.

Understand WebSocket Passthrough

A WebSocket connection starts with a handshake. The client connects to APIM, APIM connects to the backend, and the gateway brokers messages after the upgrade. Each established connection maps one client to one backend; it is not load-balanced message by message across several backends.

APIM creates an onHandshake operation where supported policies inspect the initial request. Do not assume an HTTP body transformation or validation policy runs on every subsequent WebSocket message. Policy support and connection limits must be checked for this protocol and gateway.

The Azure and developer portal consoles support connection and message testing. A successful 101 upgrade is only the start: verify messages in both directions, disconnection behavior, backend certificate trust, and diagnostic logs. WebSocket APIs are not supported in Consumption; check the current feature matrix for your target tier.

Develop Against an Agreed Contract

In a design-first workflow, agree the operations, schemas, status codes, and examples with consumers before implementation. Import that definition and use mock responses to let frontend and backend teams work independently. A mock proves what a consumer expects; it does not prove that the real backend implements it.

For the Catalog API, a useful contract includes the list response, a single-product response, and a documented missing-product error. Include examples and schemas for each relevant response rather than documenting only 200. Compare the generated or implemented backend with the agreed definition during integration tests.

Code generation or scaffolding can create implementation skeletons from a definition, but support depends on the selected generator, language, and runtime. The presentation's historical Functions scaffolding language list is not a guarantee of current tooling support. The required lab uses the supplied .NET 10 implementation instead of depending on that older extension workflow.

How to choose

Use code-first when an implementation is your starting point; use design-first when early contract review and parallel consumer development matter. Both approaches need compatibility tests and intentional documentation.

Use VS Code for More Than Backend Editing

The Azure API Management extension provides a resource-oriented view of your APIM services and APIs. It complements the backend language tools: editing a C# endpoint, editing an OpenAPI definition, and editing a gateway policy are different operations with different deployment effects.

Use the extension's API and policy editing capabilities alongside HTTP requests and contract inspection. XML tooling can identify structural problems, but a policy expression can still fail at gateway runtime. Keep policy source and environment-specific configuration under review before applying changes.

The current extension also supports assisted policy authoring and explanation with GitHub Copilot for Azure. Treat generated policies as drafts: check their scope, supported gateway, effective inheritance, and denied-request behavior. For step-through diagnosis, see policy debugging and its access restrictions.
