Separate the Trust Boundaries

flowchart LR
    C[Consumer identity] --> G[APIM gateway]
    K[Subscription key] --> G
    G --> B[Backend authentication]
    B --> F[Backend service]
    P[Management identity] -.-> G
    class C,P external
    class K neutral
    class G,F azure
    class B success

Blue services execute the request. Green represents a separate backend trust check; a gray subscription key is not the consumer's identity.

A subscription key enables access under an APIM subscription. It is not the same as an Azure subscription and does not establish an end user's identity. Use identity-aware validation when your API needs user or application claims.

Backend authentication is independent of the caller's APIM key. Your backend must reject unwanted direct calls if bypassing the gateway would violate your security model.

Validate Identity Rather Than Just Reading Credentials

APIM can enforce subscription keys without a custom authentication policy when the API requires a subscription. Keys are useful for access plans and attribution, but possession of a shared key does not identify a person or prove permission to a specific business record.

For bearer tokens, validate-jwt validates a token against configured signing information, issuers, audiences, expiry requirements, and required claims. OpenID Connect discovery can supply signing configuration. The validate-azure-ad-token policy is the purpose-specific option for Microsoft Entra tokens. Decoding a token is not signature validation, and a valid signature alone is not sufficient authorization.

Choose the expected issuer and audience deliberately: a token intended for a different API should not become valid simply because you trust its identity provider. Required scopes or roles must match the operation, and the backend still owns resource-level rules such as which account a caller may read.

For certificate-based callers, validate-client-certificate checks the presented certificate against validation rules and selected identity properties. Plan trust, revocation, validity dates, and renewal, and verify how your gateway requests and receives client certificates. This inbound check is separate from authentication-certificate, which authenticates APIM to a backend.

Important: a developer portal OAuth test configuration is not a substitute for enforcing a token-validation policy at the gateway. Test missing credentials, expired credentials, wrong audience, and insufficient permissions as separate cases.

Protect the Data, Management, and User Planes

PlaneThreat or failure to considerControls to evaluate
Data: gateway and backend callsUnauthorized callers, abusive volume, invalid payloads, direct backend bypassIdentity validation, backend authentication, schema validation, traffic controls, and suitable network isolation.
Management: service configurationUnreviewed policy or credential changesLeast-privilege Azure RBAC, controlled deployment identities, review gates, and activity logs.
User: developer onboardingIncorrect portal access, product visibility, or subscription approvalSupported identity providers, product/group design, approval rules, and consumer-account testing.

IP filtering and private networking constrain reachability, but neither expresses every business authorization rule. WAF and DDoS protections are complementary platform services, not a promise that creating APIM prevents every attack. Verify the chosen network and perimeter architecture for the actual tier.

Keep secrets and certificates in appropriately managed stores and separate them from policy source. Use named values and secret references to centralize configuration, but still review who may modify policies and where resolved values can appear.
